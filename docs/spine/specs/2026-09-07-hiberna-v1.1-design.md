# hiberna v1.1 - severity and navigation

- **Date:** 2026-09-07
- **Stage:** design approved in conversation, recorded here as the spec
- **Baseline:** v1 merged to main, 209 tests, verified on an API 36 emulator
  with Shizuku actually running

## Why

Two weaknesses the owner found by using the app on a device:

1. hiberna only ever **warns**. It never says "safe" or "worth restricting", so
   a list of hundreds of apps gives you nowhere to start. The original
   NoMoreBackground sorted this with severity tiers; v1 built only the warning
   half.
2. Navigation is threadbare. Back works, but there is no app bar, no title, no
   back affordance, and tapping a row opens a detail sheet nothing hints at.

## 1 - Severity model

Built **entirely from signals hiberna already reads**. No new permissions, no
`batterystats` parsing, nothing that can contradict the Settings app. That
constraint is deliberate: this app's credibility rests on agreeing with the
system, and a computed battery percentage that disagrees with Settings would
cost more than it gains.

| Tier | Meaning | Driven by |
|---|---|---|
| `RECOMMENDED` | Free to run all night with no reason to be | Battery-whitelisted or Unrestricted, AND no sensitive signal |
| `SAFE` | Ordinary app, no background signals | Nothing detected |
| `CAUTION` | Restrict only if you know what it does | A system app, or one whose sensitivity detection failed (`Sensitivity.UNKNOWN`) |
| `WILL_BREAK` | Something visible stops working | Role holder (SMS / dialer / assistant / launcher), authenticator, alarm handler, or a foreground service declaring location, health **or media playback** |

**Decisions already made:**

- `RECOMMENDED` is **opinionated** - hiberna actively says "restrict these".
  The owner accepted the trade: it will occasionally recommend something they
  would rather keep, and that is a trust cost worth paying over an app with no
  opinion.
- The existing guardrail becomes the top tier of this scale rather than a
  parallel concept. `Sensitivity.LIKELY_BREAKS` maps to `WILL_BREAK` and
  `Sensitivity.UNKNOWN` must keep behaving conservatively.
- Bulk apply keeps skipping `WILL_BREAK` by default, exactly as it skips
  `LIKELY_BREAKS` today. The shared `isSkippedByGuardrail` predicate stays
  the single expression of that decision.
- The list **sorts by tier**, Recommended first. That is the whole payoff: it
  answers "where do I start".

**Corrected 2026-09-07, during implementation.** The first draft of this table
put media-playback foreground services in `CAUTION` and only location/health in
`WILL_BREAK`. That split was arbitrary and wrong: restricting a music player
stops background audio, which is exactly as visible a breakage as losing
turn-by-turn navigation. All three foreground-service types belong in
`WILL_BREAK`, which is also how `SensitivityDetector` already classified them -
the detector was right and the table was wrong. `CAUTION`'s real drivers are
system apps and failed detection.

**Invariant to preserve:** the honesty rule. A tier is derived from state read
back from the system, never from state the user requested.

## 2 - Navigation

- A top app bar on every screen. Brutalist: Ink bottom border, no Compose
  `elevation`, Archivo title, radius 0.
- Back affordance on Presets and on the detail sheet. The list keeps its
  Presets action.
- Make the row detail **discoverable** - today tapping a row opens a sheet and
  nothing indicates it.
- Surface the **system-apps toggle**. It is already plumbed through
  `AppListViewModel` with no UI at all - a gap recorded during v1.
- A close affordance on the detail sheet, not only back and the scrim.

## Out of scope

- Per-app battery percentages. Deferred with reasons recorded: the figure is
  computed by a hidden power model rather than read, `BatteryStatsManager` is
  largely `@SystemApi`, `dumpsys batterystats` output is undocumented and
  version-fragile, and its window (since last full charge) is wrong for the use
  case. The detail sheet's "Open in Settings" already reaches the OS's own
  figure.
- Ranking by real usage via `UsageStatsManager` - it needs the
  `PACKAGE_USAGE_STATS` special access, which dents the one-permission story
  `PRIVACY.md` leans on.
- Preset creation and value editing (still deferred from v1).
- A `BrutalSwitch` to replace the stock rounded Material3 switches.
